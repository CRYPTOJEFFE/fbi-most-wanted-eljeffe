schema and relationship inspection work without adding Python runtime dependencies.

## Model structure

The JSON has `version`, `schemata`, and `types` keys. Each schema's `properties`
contains its own definitions; `extends` lists direct parents; `schemata` includes
the full ancestry and the schema itself. Resolve inherited properties before
checking a record. For example, `Person` inherits `LegalEntity` and `Thing`.

An entity reference is a property whose definition has `type: "entity"`.
Match references only in these properties and only within the appropriate source
snapshot. A name or note equal to another entity's ID is not a relationship.
Some reference definitions have `stub: true`: these are reverse properties
generated by the ontology. They are not plain URLs. For example, `Person.images`
is a reverse relation to `Image.pictured`; it is not a place to store image URLs.

To build a reference-property mapping from the snapshot:

```python
import json
from pathlib import Path

model = json.loads(Path("eljeffe/ftm_model.json").read_text(encoding="utf-8"))

def properties_for(schema_name):
    schema = model["schemata"][schema_name]
    properties = {}
    for parent in schema.get("extends", []):
        properties.update(properties_for(parent))
    properties.update(schema.get("properties", {}))
    return properties

reference_properties = {
    name: sorted(
        prop for prop, definition in properties_for(name).items()
        if definition.get("type") == "entity"
    )
    for name in model["schemata"]
}
```

The snapshot supports checks of schema names, property names, inheritance,
reference types, required-property metadata and declared length or enum metadata.
It does not implement every normalization or validation algorithm of the
upstream Python library. Do not describe a structural check as full upstream
type validation.

## Updating or regenerating

For an exact repeat of this snapshot, fetch the immutable blob above, decode its
GitHub `content` payload if returned as base64, and verify the local file:

```sh
git hash-object eljeffe/ftm_model.json
```

The expected output is the Git blob SHA listed above. For a newer snapshot, review
the upstream release and license, replace the file from that release's
`js/src/defaultModel.json`, and update the version, source SHA, size and tests in
this project. Do not silently fetch a moving branch at application startup.

The official library can also generate the model in a separate development
environment. These commands are optional; the application does not require this
environment:

```sh
python3 -m venv .venv-ftm
.venv-ftm/bin/python -m pip install "followthemoney==4.11.3"
.venv-ftm/bin/ftm dump-model -o ftm-model.generated.json
.venv-ftm/bin/ftm validate -i sample.ftm.json -o sample.normalized.ftm.json
```

On Windows, use `py -3 -m venv .venv-ftm`, then the corresponding executables
`.venv-ftm\\Scripts\\python.exe` and `.venv-ftm\\Scripts\\ftm.exe`.

Compare the normalized output to the original input by entity ID and property
values. The official `ftm validate` command cleans values and drops invalid
values; a successful exit alone does not establish lossless schema compliance.
Do not overwrite source evidence with its cleaned output.
